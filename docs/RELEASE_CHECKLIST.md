# Reproducible release checklist

Use this for a **new** version after review. It does not authorize a tag, merge, upload or deployment. Existing 0.2.36 assets stay immutable. Check boxes only when the exact candidate passes; link failed and skipped checks too.

1. Record branch, `git status --short`, `git rev-parse HEAD`, baseline and diff. Inspect open issues/PRs and previous evidence before repeating work. Resolve version agreement between manifest, Python package and runtime; keep proposed changes under Unreleased until release approval.
2. Use mise Python/uv pins. Provision reviewed dependencies before isolating tests. Use a credential-free disposable machine/container: no network, no host home or sockets, read-only tools, scratch-only writes and bounded CPU/memory/process/disk/time. Do not copy CI's `sudo` or sysctl preparation onto the workstation.
3. Run `mise exec -- uv run --offline python -m unittest discover -s tests -v`, `node --test tests/model.test.cjs`, and `mise exec -- uv run --offline python tools/verify_publication.py`. Record counts, skips and exit status.
4. On a disposable Omarchy environment with local PySide6 dependencies, run `mise exec -- uv run --offline python tools/verify.py --ui-python /path/to/ui-python --sensor-engine /path/to/pinned/falco`. This includes QML, manifest, Ruff, systemd syntax, policy, UI, offline report/baseline/AI-packet and reproducible package/install/remove checks. A missing engine or UI runtime is a gate, not a silent skip. Policy dry-run does not attach to the kernel.
5. Generate SBOM twice with `mise exec -- uv run --offline python tools/generate_sbom.py --output dist/sbom-a.json` and `--output dist/sbom-b.json` (create `dist` first), compare with `cmp`, inspect component scope, hashes and dependency edges, and validate CycloneDX 1.6 against a locally pinned official schema. Record advisory database date, exact ecosystems queried and unresolved matches. No advisory matches is not security clearance.
6. Complete the [fresh-VM matrix](ACCEPTANCE_TESTS.md), especially explicit AI action, root helper provenance, reboot and removal. Mark any release-blocking acceptance rows not run. Review same-user/root, kernel, scanner/parser and provider-client limitations.
7. From a clean reviewed commit, run `mise exec -- uv run --offline python tools/prepare_release.py --require-clean --tag vX.Y.Z --output dist/candidate-X.Y.Z`. Use a new directory; never replace conflicting assets. Verify source commit, clean flag, manifest version, artifact hash and file inventory. If the tag already exists, explicitly compare `git rev-parse 'vX.Y.Z^{commit}'` to the manifest source commit; the builder currently validates the tag spelling, not its Git target.
8. Resolve the P1 native dependency gates for anyhow and tokio in [advisory triage](SUPPLY_CHAIN_REVIEW.md): document actual build/call reachability, remediate affected dependencies or obtain an explicit maintainer disposition supported by evidence. Do not describe the current binary as cleared. Independently rebuild any changed native library with its exact pinned toolchain and inputs, inspect notices/licenses, compare hashes and pass exact-binary VM acceptance before a new native release. Retain outstanding gates visibly; deterministic tar packaging is not deterministic native compilation.
9. Inspect every proposed public file and nested archive. Exclude `.env`, credentials, private reports, personal paths, local logs, screen captures of real data and development history. Run publication checks again. Keep a short sanitized evidence summary, not raw local evidence.
10. Review the diff, new tests, SBOM and claims; open a feature-branch PR. Require its CI to finish and record the reviewed revision. No direct default-branch pushes. A reviewer/maintainer decides merge and future release; nothing in this checklist auto-publishes.
11. After separate release approval, verify published bytes against the approved candidate, then request marketplace review of the new exact snapshot. Do not carry the October 25 verification badge forward as assurance of changed code. Post launch copy only after separate publishing authorization.

See [current status](../POST_LAUNCH_STATUS.md), [security scope](../SECURITY_REVIEW.md) and [contributor checks](CONTRIBUTOR_TESTING.md). Community Ironclad stays free; no fleet telemetry or mandatory account may be introduced by release tooling.
